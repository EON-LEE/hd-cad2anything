# 데모 런북

## 1. 목적과 범위

이 문서는 CAD2Anything PoC 데모를 준비하고, 진행하고, 정리하는 절차다. 독자는 데모 진행자다.

- 모든 도면과 거래 데이터는 합성 데이터다. 브랜드 이름은 가상이다.
- 명령은 저장소 루트에서 PowerShell로 실행한다.
- 리소스 이름은 `infra/README.md`의 배포 출력값을 쓴다. 이 문서에는 실제 주소와 구독 정보를 적지 않는다.

## 2. 구성 요약

| 구성 요소 | 역할 |
|---|---|
| Atlas 서비스(Container App 1개) | 웹 화면, REST·채팅 API, MCP 엔드포인트(`/mcp`) |
| Foundry 에이전트 7개 | Orchestrator와 전문 에이전트 6개. 구성은 `agents/agents.yaml`에 있다. |
| PostgreSQL + PostGIS | 작업공간 미러(`workspace_file` 테이블)와 공간 질의 |
| 모델 배포 | `gpt-6.1-sol`(250K TPM), `gpt-5.4-mini`(150K TPM) |

## 3. 사전 준비

**전제조건**

- `az login`으로 데모 구독에 로그인되어 있다.
- 개발자 계정에 `infra/README.md`의 개발자 역할이 할당되어 있다.
- `uv`, Node.js, Azure CLI가 설치되어 있다.
- 개발 PC의 공인 IP가 PostgreSQL 방화벽 규칙에 등록되어 있다.

**절차**

1. 합성 도면을 생성한다.

   ```powershell
   uv run --no-sync python -m cad2anything.mockgen.drawings --out data/generated --seed 42
   ```

2. 합성 업무 데이터를 생성한다. 기본 표본 비율은 0.02다.

   ```powershell
   uv run --no-sync python -m cad2anything.mockgen.business --out data/generated --seed 42
   ```

3. 미러 설정을 지정한다.

   ```powershell
   $env:WORKSPACE_MIRROR = 'postgres'
   $env:POSTGRES_HOST = '<PostgreSQL 서버 FQDN>'
   $env:POSTGRES_USER = (az account show --query user.name -o tsv)
   ```

4. 도면을 파싱해 작업공간을 만들고 미러에 올린다.

   ```powershell
   uv run --no-sync python -m cad2anything.bootstrap --mode parse --push
   ```

5. 공간 질의용 PostGIS 테이블을 동기화한다.

   ```powershell
   uv run --no-sync python -m cad2anything.store.postgis sync --root data/workspace
   ```

6. 점검표를 실행한다. 모든 항목이 `통과`인지 확인한다. 하나라도 `실패`이면 데모를 진행하지 않고 원인을 확인한다.

   ```powershell
   uv run --no-sync python -m cad2anything.evaluation.scorecard --root data/workspace --truth data/generated/truth
   ```

7. 이미지를 빌드하고 서비스와 에이전트를 배포한다. 절차는 `infra/README.md`의 "서비스 배포"를 따른다.
8. 서비스가 작업공간을 읽었는지 확인한다. `GET <atlas-url>/healthz`의 `revisions`에 `R0`, `R1`, `R2`, `H1`이 있어야 한다. 개편 대안을 만든 뒤에는 `FW2026-A0` 같은 가상 개정도 함께 나온다.
9. 시즌 개편과 다점포 비교 데모용 메타데이터가 있는지 확인한다. `GET <atlas-url>/api/uploads/metadata`에서 `leases`, `stores`, `store_kpis`의 `present`가 `true`이고, `relayout_brief`의 `items`에 `FW2026`이 있어야 한다. 없으면 Atlas의 개정 검토 탭 → 메타데이터에서 `data/samples/metadata/`의 파일을 올린다: `leases.csv`(종류: 계약), `FW2026.yaml`(종류: 개편 브리프), `stores.csv`(종류: 비교 점포), `store_kpis.csv`(종류: 점포 실적). 4단계의 `bootstrap`으로 만든 작업공간에는 이미 들어 있다.
10. 데모 전에 4절의 질문 하나를 실행한다. 첫 분석 요청은 거래 데이터를 메모리에 올리므로 다른 요청보다 느리다.

**완료 기준:** 6단계의 점검표가 모두 통과하고, 8단계의 기준 개정 네 개와 9단계의 메타데이터가 있고, 10단계의 질문이 `RUN_FINISHED`로 끝난다.

## 4. 데모 시나리오

질문은 Atlas 채팅 창에 입력한다. 응답 시간은 도구 호출 수에 따라 달라진다. 2026-10-21 평가에서는 대부분의 질문이 60초 안에 끝났고, 레이아웃 대안과 업계 조사처럼 전문 에이전트나 웹 검색을 거치는 질문은 100~140초가 걸렸다. 채팅은 진행 중인 단계를 한 줄(예: "4층 공간 생산성 계산")로 보여 주고, 답변은 생성되는 대로 표시한다. 진행자는 응답을 기다리는 동안 이 단계를 설명한다. 끝난 단계 목록은 답변 위에 접혀 있으며 펼쳐 볼 수 있다.

**설명할 때 지킬 것**

- 매출과 ㎡당 매출은 합성 표본 거래를 전체 규모로 환산하고 연 단위로 환산한 값이라고 밝힌다.
- 요인 분해, 인접 효과, 레이아웃 대안은 추정치다. 인과 효과로 설명하지 않는다.
- 고객 동선은 결제 순서와 시각을 통로망의 최단 경로로 이은 추정이다. 실제로 걸은 경로가 아니다. 실제 동선을 보려면 Wi-Fi, 비콘, 카메라 같은 위치 데이터와 고객 동의가 필요하다. 고객 ID는 가명이다.
- 방향(동·서·남·북)은 도면 기준이다(도면 위쪽=북). 메인 동선(`traffic_potential`)은 도면 구조로 계산한 잠재 유동이며 관측한 유동이 아니다. 길 찾기의 걷는 거리에는 에스컬레이터·엘리베이터를 타는 구간이 들어가지 않는다.
- 산출물 승인은 에이전트가 하지 않는다. 사람이 개정 검토 탭에서 승인하거나 반려한다.
- 개편 대안은 LLM이 고르지 않는다. 최적화 코드가 브리프의 조건(목적, 이동 대상, 최대 이동 수, 공사 기간)으로 계산하고, 대안 결정은 사람이 한다. 계산 방법은 `docs/specs/mcp-tools.md` 5절에 있다. 공사 순서도 같은 방식으로 코드가 계산한다(5.2절).
- 추정 유동과 팝업 후보는 여러 고객의 결제 순서를 통로망 최단 경로로 이어 모은 값이다. 실제로 걸은 길이나 관측한 유동이 아니다. 통로 폭·피난 거리 점검은 도면으로 계산한 참고값이며 법규 판정이 아니다.
- 다른 점포 실적은 합성 메타데이터다. 실제 비교에는 각 점포의 같은 기준 실적을 받아야 한다.
- 업로드 시연의 "고객사 형식" 도면은 합성 도면이다. 실제 고객 도면 규약은 고객 도면을 받아 프로필로 맞춰야 한다.

## 5. 문제 대응

| 증상 | 확인할 것 | 조치 |
|---|---|---|
| 채팅이 `RateLimitError`로 끝난다. | 모델 배포의 분당 토큰 한도 | 1분 뒤 같은 질문을 다시 보낸다. 반복되면 모델 배포 용량을 확인한다. |
| `/healthz`의 `revisions`가 빈 목록이다. | 미러 적재 여부 | 3절 4단계를 다시 실행한 뒤 Container App 리비전을 다시 시작한다. |
| 생산성 결과가 "가상 개정에는 거래 실적이 없습니다"로 끝난다. | 선택한 개정의 종류 | R0, R1, R2 중 하나를 선택한다. 가상 개정은 레이아웃 도구로 추정한다. |
| 생산성 결과가 "아직 거래 실적이 없습니다"로 끝난다. | 선택한 개정의 적용일 | 업로드한 다음 시즌 도면처럼 적용일이 거래 데이터 뒤인 개정이다. 실적이 있는 개정을 고르거나 기대 매출(추정치)로 본다. |
| 시즌 개편 질문에 "개편 브리프 FW2026가 없어요"라고 답한다. | `GET /api/uploads/metadata`의 `relayout_brief` | 3절 9단계대로 브리프와 계약 정보를 올린다. |
| 업로드 작업이 `needs_review`로 끝난다. | 작업 상세의 레이어 검토 큐 | 레이어마다 의미를 고르고 "매핑 저장 후 다시 처리"를 누른다. 고객사 형식 도면이면 프로필을 먼저 올리고 그 프로필로 다시 올린다. |
| 업로드 작업이 `failed`로 끝난다. | 작업의 `error` 메시지 | 파일 이름에 층 코드가 있는지, 부모 개정과 적용일이 맞는지 확인하고 다시 올린다. 앱을 다시 시작하면 진행 중이던 작업은 실패로 바뀐다. |
| 앱 로그에 `/mcp` 401 응답이 있다. | 앱 비밀과 Foundry 프로젝트 연결의 MCP 키 | `infra/services.bicep`을 다시 배포한다. 이 배포는 두 값을 함께 바꾼다. |
| 히트맵이 비어 있다. | 개정과 층, 지표 | 가상 개정에서는 `sales_per_m2`와 `sales_krw`만 기대 매출 추정치로 표시된다. |
| 새 리비전이 준비되지 않는다(`ActivationFailed`, `0/1 replicas ready`). 앱 로그에 `psycopg ... ConnectionTimeout`이 있다. | PostgreSQL 서버 상태(`az postgres flexible-server show --query state`). 사용자가 아닌 자동화가 서버를 중지할 수도 있으므로 활동 로그에서 중지한 주체를 확인한다. | 서버를 시작한 뒤 실패한 리비전을 다시 시작한다(7절). 이미 실행 중인 리비전은 시작할 때 내려받은 작업공간으로 계속 동작한다. 그러나 새로 배포하거나 다시 시작한 리비전은 미러에 연결하지 못하면 시작하지 못한다. |

## 6. 데모 초기화

데모 중 만든 가상 개정(H2 이후, 개편 대안 `FW2026-A*`), 업로드한 개정과 메타데이터, 개편 프로젝트, 산출물 승인 상태는 미러에 저장되어 앱을 다시 시작해도 남는다. 다음 데모를 처음 상태에서 시작하려면 아래 절차를 실행한다.

> **주의:** 이 절차는 미러에서 기준 데이터에 없는 파일을 모두 삭제한다. 보존할 가상 개정이나 산출물이 있으면 먼저 내려받는다.

1. 3절 3단계의 미러 설정을 지정한다.
2. 작업공간을 처음부터 다시 만들고, 미러에 올리고, 기준 데이터에 없는 미러 파일을 삭제한다.

   ```powershell
   uv run --no-sync python -m cad2anything.bootstrap --mode parse --clean --push --prune
   ```

3. Container App 리비전을 다시 시작한다. 새 컨테이너가 미러에서 작업공간을 내려받는다.

   ```powershell
   az containerapp revision restart --resource-group <리소스 그룹> --name <Container App 이름> --revision <활성 리비전 이름>
   ```

4. `GET <atlas-url>/healthz`의 `revisions`가 `["R0","R1","R2","H1"]`인지 확인한다.

## 7. 비용 통제와 정리

**상시 비용이 드는 리소스:** Container App(복제본 1개 상시 실행), PostgreSQL(B1ms), Container Registry(Basic), Log Analytics, Storage, Key Vault. 모델 배포(GlobalStandard)는 사용한 토큰만큼 과금된다.

**데모가 없는 기간**

1. PostgreSQL 서버를 중지한다. 중지한 서버는 최대 7일 뒤 자동으로 다시 시작된다.

   ```powershell
   az postgres flexible-server stop --resource-group <리소스 그룹> --name <PostgreSQL 서버 이름>
   ```

2. 데모를 다시 시작할 때 PostgreSQL 서버를 시작한 뒤 Container App 리비전을 다시 시작한다. 앱은 시작할 때 미러에서 작업공간을 내려받는다.

**PoC 종료**

> **경고:** 다음 명령은 리소스 그룹의 모든 리소스와 데이터를 삭제한다. 되돌릴 수 없다. 실행 전에 필요한 결과물을 저장한다.

```powershell
az group delete --name <리소스 그룹>
```

## 8. 알려진 한계

- 실제 도면과 거래 데이터로 검증하지 않았다. 고객 도면으로 파싱 규칙을 확인하고 도면 규약 프로필을 만들어야 한다.
- DXF만 지원한다. DWG 변환 경로와 외부 DWG 테스트 도면은 라이선스를 확인한 뒤 결정한다.
- Atlas 웹과 API에는 사용자 인증이 아직 없다. MCP 엔드포인트만 키로 보호한다. 데모 주소를 공유하기 전에 인증 적용 여부를 결정해야 한다. 업로드 API도 인증 없이 열려 있다.
- 도면 업로드는 Atlas 안에서 한 번에 하나씩 처리한다. Event Grid 기반 자동 처리와 여러 작업의 동시 처리는 없다.
- 작업공간을 메모리에 두므로 복제본을 1개로 고정한다.
