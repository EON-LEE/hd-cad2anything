# Atlas 웹앱 (atlas-web)

Atlas는 백화점 운영사를 위한 에이전트 기반 공간 분석 웹앱이다. 도면 캔버스, 에이전트 채팅, 개정 검토, 레이아웃 대안, 관계 그래프를 한 화면에서 제공한다.

에이전트(백엔드)는 화면을 직접 그리지 않는다. 에이전트는 채팅 응답 스트림에 `STATE_DELTA` 이벤트를 보내고, 웹앱은 이 이벤트로 UI 상태를 바꾼다. 계약은 [Atlas API 계약](../../docs/specs/atlas-api.md)을 따른다.

- **STATE_DELTA:** UI 상태에 적용할 JSON Patch(RFC 6902) 배열을 담은 이벤트다.
- **좌표:** 도면은 건물 남서쪽 모서리를 원점으로 하는 로컬 미터 좌표다. 지도 타일과 위경도를 쓰지 않는다.
- **데이터:** 모의 데이터의 브랜드명은 모두 가상이다.

## 1. 요구 사항

| 항목 | 버전 | 비고 |
|---|---|---|
| Node.js | 24 LTS(24.15 이상) 권장 | Vite 8은 20.19 이상 또는 22.12 이상이 필요하다. 테스트 도구(Vitest 5, jsdom 30)는 22.22.2 이상 또는 24.15 이상이 필요하다. |
| npm | Node.js에 포함된 버전 | 레지스트리 설정을 바꾸지 않는다. |
| 백엔드 | `atlas-api`(FastAPI) | 없으면 모의 모드로 실행된다. |

`package-lock.json`은 사용하는 레지스트리 주소를 기록하므로 Git에서 제외한다.

## 2. 실행

모든 명령은 `apps/atlas-web` 폴더에서 실행한다.

### 2.1 설치

```powershell
npm install
```

### 2.2 백엔드와 함께 실행

1. 백엔드 `atlas-api`를 `http://localhost:8000`에서 실행한다.
2. 개발 서버를 실행한다.

   ```powershell
   npm run dev
   ```

3. 브라우저에서 `http://localhost:5173`을 연다.

개발 서버는 `/api` 요청을 `http://localhost:8000`으로 전달한다. 백엔드 주소가 다르면 개발 서버를 실행하기 전에 `ATLAS_API_URL` 환경 변수를 지정한다.

```powershell
$env:ATLAS_API_URL = 'http://localhost:8010'; npm run dev
```

### 2.3 모의 모드로 실행

모의 모드는 백엔드 없이 `src/mock/`의 내장 데이터로 동작한다. 아래 방법 중 하나를 사용한다.

| 방법 | 명령 또는 동작 |
|---|---|
| npm 스크립트 | `npm run dev:mock` |
| 환경 변수 | `$env:VITE_MOCK = '1'; npm run dev` |
| 환경 파일 | `.env.example`을 `.env.local`로 복사하고 `VITE_MOCK=1`로 바꾼다. `.env.local`은 Git에서 제외된다. |
| URL 매개변수 | 주소 끝에 `?mock=1`을 붙인다. 빌드 결과물에서도 동작한다. |
| 자동 전환 | `GET /api/meta`가 실패하거나 8초 안에 응답하지 않으면 모의 모드로 전환한다. |

모의 모드에서는 상단에 `모의 데이터` 배지와 전환 사유가 표시된다.

### 2.4 빌드

```powershell
npm run build
```

- `tsc -b`로 타입을 검사한 뒤 `vite build`를 실행한다. 타입 오류가 있으면 빌드가 실패한다.
- 결과물은 `apps/atlas-web/dist`에 생성된다. 이 폴더는 Git에서 제외한다.
- FastAPI 백엔드가 `dist`를 `/` 경로에서 제공하는 것을 전제로 `base`를 `/`로 설정했다. 자산 경로는 `/assets/`이다.
- 작업 중인 백엔드 구현(`src/cad2anything/services/atlas_api.py`)은 `ATLAS_WEB_DIR` 환경 변수로 지정한 폴더를 `/`에 연결한다. 이 경우 `ATLAS_WEB_DIR`에 `apps/atlas-web/dist`의 경로를 지정한다.
- `npm run build:mock`은 모의 모드를 고정한 결과물을 만든다.
- `npm run preview`는 빌드 결과물을 로컬에서 확인한다. 이때도 `/api` 프록시가 동작한다.

## 3. 화면 구성

| 영역 | 기능 |
|---|---|
| 상단 바 | 제목, 개정 선택(`/api/meta`), 개정 비교 켜기와 비교 기준 개정 선택, 층 탭(`/api/meta`의 층 목록). 고객 동선이 있으면 결제가 있는 층 탭에 결제 수를 주황 배지(오른쪽 위)로 표시한다. 길 찾기 경로가 있으면 경로가 지나는 층 탭 왼쪽 위에 파란 점을, 통로 집계가 있으면 구간이나 표시 지점이 있는 층 탭 왼쪽 위에 보라 점(통로 폭·피난 점검은 빨간 점)을 표시한다. 표시는 탭 너비를 바꾸지 않는다. |
| 도구 막대 | 집기·통로·라벨 레이어, 확대·축소·전체 보기, heatmap 끄기, 강조·연결 지우기 |
| 도면 캔버스 | deck.gl `OrthographicView`로 그린다. 매장은 카테고리 색 또는 heatmap 색으로 칠한다. 통로, 수직동선(에스컬레이터·엘리베이터·계단)과 라벨, 편의시설, 출입구, 집기, 매장 라벨, 통로 집계, 강조 외곽선, 연결선, 길 찾기 경로, 고객 동선을 표시한다. 통로 집계의 선과 표시 지점에 마우스를 올리면 구간 이름과 값(예: "1,234명(추정)", "폭 3m"), 후보 제목을 툴팁으로 보여 준다. |
| 범례 | 카테고리, heatmap 척도, 개정 비교 색, 강조 사유, 연결선 설명, 통로 집계(모드 이름, 적음~많음 색 막대, 백엔드가 정한 선 색, 표시 지점 종류, 단위와 설명), 길 찾기 경로(선, 출발·도착 표시, "통로망 최단 경로 · 걷는 거리 85m"), 고객 동선(선, 번호 표시, "결제 순서 기반 추정 경로")을 글자로 표시한다. 동선 카드가 닫혀 있으면 "동선 목록 보기" 버튼을 표시한다. |
| 매장 상세 카드 | 매장을 누르면 브랜드, 카테고리, 면적, KPI(`/api/analytics/productivity`)를 표시한다. |
| 통로 집계 상자 | `flow`가 있으면 도면 왼쪽 위에 띄운다. 모드 표시("추정 유동", "팝업 후보", "통로 폭·피난 점검"), 제목, 요약 칩(추정 유동·팝업 후보: "고객-일 1,234", "이동 4,567건", "2개 층", "후보 4곳". 통로 폭·피난 점검: "좁은 통로 3곳", "피난 거리 초과 2곳", 기준 폭·거리), 표시가 있는 층, 표시 지점 목록(순위와 제목, 처음 5곳), 주의 문구, "표시 지우기" 버튼이 있다. 층이나 표시 지점을 누르면 그 층 도면으로 바꾸고, 매장 코드가 있는 지점은 그 매장에 초점을 맞춘다. 화면의 개정이 `flow.rev`와 다르면 어느 도면으로 계산했는지 알린다. |
| 길 찾기 상자 | `route`가 있으면 도면 왼쪽 위에 띄운다. "길 찾기" 표시, 제목(출발 → 도착), 요약 칩("걷는 거리 85m", "에스컬레이터 A · 7개 층 이동 · 높이 35m"), 경로가 지나는 층("1층 출발 → 8층 도착"), 주의 문구, "경로 지우기" 버튼이 있다. 층을 누르면 그 층 도면으로 바꾼다. 화면의 개정이 `route.rev`와 다르면 어느 도면으로 계산한 경로인지 알린다. |
| 고객 동선 카드 | `panel.type = journey`일 때 도면 왼쪽 위에 띄운다. 요약 칩, 결제 순서 타임라인(시각, 층, 브랜드·카테고리, 금액, 앞 결제와의 간격, 층 이동), 주의 문구, "다른 고객 보기"·"닫기"·"동선 지우기" 버튼이 있다. 결제 항목을 누르면 그 층으로 가서 매장에 초점을 맞춘다. |
| 에이전트 탭 | 대화형 채팅. 사용자 질문은 오른쪽 말풍선, 답변은 말풍선 없는 본문으로 표시한다. 실행 중에는 상태 한 줄, 답변 위에는 접힌 작업 과정을 표시한다(4절). 처음에는 소개와 추천 질문 7개를 표시하고, 대화가 시작되면 입력창 위에 한 줄로 줄인다. "새 대화"는 대화를 지운다. |
| 개정 검토 탭 | 유형별 변경 목록, 영향 분석(생성기, 위험도, 승인 방식), 산출물 목록, 승인·반려. 위쪽의 "도면·메타데이터 올리기"를 펼치면 도면 업로드와 메타데이터 업로드를 한다(3.1절). 보고 있는 개정이 이전 개정을 바꾼 실제 개정이고 적용 기간에 실적이 있으면(`has_sales: true`, 예: R1, R2) 머리글 아래에 "개편 성과 보고서(90일) 열기" 링크와 비교 기간(30일·90일) 선택을 표시한다. 링크는 `/api/reports/relayout-review/{rev}?window_days=90`을 새 탭으로 연다. |
| 레이아웃 대안 탭 | "시즌 개편"(3.1절)과 "배치 대안" 두 화면. 배치 대안은 대안 생성 요청, 이동 목록, 목적함수, 매출 영향 범위, 제약 충족 여부, 미리보기를 제공한다. |
| 관계 그래프 탭 | `state.edges`로 만든 force 그래프. 선 굵기는 weight다. 노드를 누르면 도면에서 해당 매장을 선택한다. |

개정 비교를 켜면 비교 기준 개정의 매장 경계를 보라색 선으로 겹쳐 그린다. 바뀐 매장은 `GET /api/changes/{compareRev}/{rev}`의 변경 유형에 따라 칠한다.

| 변경 유형 | 색 |
|---|---|
| 추가(`add`) | 초록 |
| 철거(`remove`) | 빨강. 현재 개정에 없는 매장은 비교 기준 개정의 도형으로 그린다. |
| 이전(`move`), 브랜드 교체(`reassign`) | 주황 |
| 면적 변경(`resize`) | 파랑 |
| 분할(`split`), 병합(`merge`) | 보라 |
| 집기 변경(`fixture_change`) | 청록 |

### 3.1 시즌 개편과 도면·메타데이터 올리기

- **시즌 개편**(레이아웃 대안 탭): 개편 브리프를 고르고 "진단하기"로 시즌 강세·약세 카테고리, 층별 전년 대비, 바꿀 후보 매장, 공실, 입점·퇴점 브랜드를 본다. "대안 만들기"는 목적(수수료 수익·매출), 최대 이동 수, 공사 기간(주), 이동 대상(계약 만료 매장만·전체)으로 대안을 만든다. 수십 초 걸릴 수 있어 경과 시간을 표시한다. 진단 결과는 대안이 생기면(`planned`·`selected`·`checked`) 접어 두고, 후보 매장은 처음 8곳만 보여 준 뒤 "모두 보기 (N)"로 펼친다(효율은 "하위 n%"). 대안 카드는 기준안(`ALT-0`)과 대안마다 요약, 순효과, 목표 변화, 이전 비용, 기준안 대비 매출 변화(범위 포함), 지금 대비 매출 변화를 보여 준다. 결정한 대안(없으면 순효과가 가장 큰 대안) 하나만 펼치고, 나머지는 "자세히"로 펼친다. 펼친 카드에는 입점·퇴점·이전을 한 줄씩, 제약은 "제약 n개 모두 충족" 또는 위반 항목만 보여 주고, 변경별 설명과 카드의 참고 사항(신규 입점 위치 조정, 이웃 매장 파급 효과)은 "근거 보기"에 둔다. "도면에서 보기"는 `rev`=대안의 가상 개정, `compareRev`=기준 개정, `floor`=처음 바뀌는 층으로 바꾼다. "이 대안으로 결정"은 결정자(기본 "MD팀")를 받아 기록한다. 대안이 있으면 "공사 순서" 블록에서 "공사 순서 계산"으로 `POST /api/relayout/{brief_id}/phasing`을 부른다. 대상은 결정한 대안(결정 전이면 순효과가 가장 큰 대안)이고, "계산 조건"을 펼치면 동시 공사 수(1~6, 기본 2), 공사 기간(주, 1~12, 기본 브리프의 공사 기간), 임시 매장 사용(기본 켬)을 바꿀 수 있다. 계산하는 동안 버튼이 "계산하는 중…"으로 바뀌고 다른 개편 동작도 기다린다. 결과는 "계산 결과"로 접을 수 있고, 대상 대안, 전체 기간, 영업 손실(추정)과 "모두 공사 기간만큼 휴점하면" 값, 입점 지연 기회 손실(0보다 클 때), 백엔드 요약, 주차별 순서 표(주차 | 매장 | 작업 | 브랜드/비고, 작업은 퇴점·이전·입점·임시 영업·휴점 칩, 처음 8단계와 "모두 보기"), "작업 설명 보기"로 펼치는 단계별 설명, 신규 입점 개점 주차(늦어진 입점은 가장 빠른 주차를 함께), 서로 자리를 바꾸는 이전(순환)의 처리, 가정과 한계를 보여 준다. 프로젝트에 저장된 공사 순서(`project.phasing`)는 다시 열 때도 보여 주고, 지금 대상과 다른 대안의 결과이면 다시 계산하라고 알린다. 결정 뒤 "도면 대조"는 CAD팀이 올린 실제 개정(기본: 기준 개정을 부모로 올린 가장 최근 업로드 개정)과 대조해 일치율, 항목별 결과(결과 칩 | 브랜드 | 계획 → 도면, 다른 항목은 강조), 계획에 없는 변경(브랜드 이름), 면적 변경을 보여 준다. "제안서 열기"는 보고서 HTML을 새 탭으로 연다.
- **도면·메타데이터 올리기**(개정 검토 탭): 도면은 층마다 DXF 또는 ZIP 1개를 올린다. 보내기 전에 계약의 규칙(개정 ID 형식, 파일 이름의 층 코드, 같은 층 중복, 파일 크기, 적용일, 업로드로 만들지 않은 기존 개정 ID)을 확인한다. 만든 작업은 2초마다 상태를 확인해 단계 진행, 도면 읽기 결과, 확인할 레이어(의미를 골라 "매핑 저장 후 다시 처리"), 변경 요약, 계약 정보 대조(오류·경고만 표로 보여 주고 참고 항목은 "참고 N건 보기"로 펼친다), 개편안 대조를 보여 준다. 작업이 끝나면 `/api/meta`를 다시 읽어 새 개정을 개정 선택에 넣고 "이 개정 보기"를 제공한다. 메타데이터는 종류(브랜드, 입점 이력, 계약, POS 단말, 개편 브리프, 도면 규약 프로필, 비교 점포, 점포 실적)를 고르고 파일을 올리면 반영·거부 결과와 종류별 현재 상태를 보여 준다. 비교 점포(`stores`)와 점포 실적(`store_kpis`)은 CSV·XLSX 표다.
- 개정 선택은 업로드로 만든 개정(`model_source: uploaded`)에 "업로드", 적용 기간에 거래 실적이 없는 실제 개정(`kind: actual`, `has_sales: false`)에 "실적 없음"을 붙인다(가상 개정은 이미 "가상"으로 표시한다). 시작 개정은 실적이 있는 가장 최근 실제 개정이다.

## 4. 상태 패치와 렌더링

채팅 요청은 `POST /api/chat`으로 보낸다. 응답은 SSE(Server-Sent Events) 스트림이다. `EventSource`는 POST를 지원하지 않으므로 `fetch`와 `ReadableStream`으로 읽는다.

질문 하나에 대한 이벤트는 실행(run) 하나로 접는다(`src/lib/chatRun.ts`). 실행은 상태(생각 중 → 작업 중 → 답변 중 → 완료 또는 오류), 단계 목록(라벨, 상위 단계, 진행 상태, 도구 이름, 인자, 요약), 답변, 시작·종료 시각을 가진다.

| 이벤트 | 웹앱의 처리 |
|---|---|
| `RUN_STARTED` | `thread_id`를 저장한다. 다음 질문에 같은 `thread_id`를 보낸다. |
| `TEXT_MESSAGE_START/CONTENT/END` | `delta`를 답변에 이어 붙인다. 첫 글자가 오면 상태 줄을 숨기고 커서와 함께 답변을 스트리밍한다. 메시지가 둘 이상이면 문단으로 잇는다. |
| `TOOL_CALL_START/END` | 단계를 만든다. 라벨은 `label`을 쓰고, 없으면 도구 이름을 한국어로 바꾼다(7절). `parent_tool_call_id`가 있으면 상위 단계 아래에 넣는다. `END`의 `label`은 시작 라벨을 바꾸고, `ok: false`는 실패로 표시한다. |
| `STATE_DELTA` | UI 상태에 패치를 적용하고 진행 중인 UI 단계에 기록한다. 도구 호출 밖에서 오면 "3층으로 이동"처럼 바뀐 내용을 라벨로 하는 단계를 만든다. |
| `RUN_FINISHED`, `RUN_ERROR` | 실행을 끝낸다. 오류는 쉬운 문장으로 알리고 기술 메시지는 접어 둔다. |

**채팅 표시**

- 실행 중에는 사용자 질문 아래에 상태 한 줄만 표시한다. 처음에는 "생각하는 중…", 그 뒤에는 진행 중인 단계의 라벨이다. 중첩 단계가 진행 중이면 "상위 라벨 · 하위 라벨"로 표시한다. 단계 사이의 짧은 공백에는 앞 라벨을 잠시 유지한다.
- 실행이 끝나면 답변 위에 "작업 과정 보기 · 4단계 · 23초"를 접어 둔다. 펼치면 단계 라벨과 완료 표시가 나오고, 중첩 단계는 들여 쓴다. UI 동작도 "4층으로 이동", "매장 5곳 강조" 같은 단계로 나온다.
- 도구 이름, 인자, `summary` 원문, 화면 갱신 기록은 기본 화면에 나오지 않는다. 펼친 목록의 "기술 정보" 버튼을 누르거나 주소에 `?debug=1`을 붙이면 표시한다.
- 오류는 "답변을 만드는 중 문제가 생겼어요. 잠시 후 다시 시도해 주세요."로 알리고 "자세히 보기" 아래에 기술 메시지를 둔다. "다시 시도"는 같은 질문을 다시 보낸다.

`STATE_DELTA`는 원자적으로 적용한다. 패치의 연산 하나라도 실패하면 이벤트 전체를 버리고 이전 상태를 유지한다. 실패하면 해당 단계를 실패로 표시하고 답변 아래에 "화면 일부를 바꾸지 못했어요."를 표시한다.

사용자의 화면 조작(층 탭, 개정 선택, 레이어 켜기·끄기, 변경 항목 보기, 대안 미리보기)도 같은 JSON Patch 경로로 상태를 바꾼다.

| 상태 경로 | 렌더링 |
|---|---|
| `/rev` | 도면, KPI, 산출물을 조회할 개정을 바꾼다. |
| `/compareRev` | 값이 있으면 개정 비교 모드로 그린다. `null`이면 비교를 끈다. |
| `/floor` | 층 탭과 도면을 바꾼다. 층이 바뀌면 선택을 해제하고 도면 전체가 보이도록 맞춘다. |
| `/layers/fixtures`, `/layers/walkways`, `/layers/labels` | 집기, 통로, 라벨 레이어를 켜거나 끈다. 집기를 켜면 `?include=fixtures`로 도면을 다시 요청한다. |
| `/heatmap` | `values`가 있으면 매장을 순차 색 척도(0=밝은 노랑, 1=남색)로 칠한다. 값이 없는 매장은 회색이다. `heatmap` 또는 `values`가 `null`이면 카테고리 색으로 칠한다. |
| `/highlights` | 해당 매장에 색 외곽선을 그린다. 사유는 범례, 툴팁, 상세 카드에 표시한다. |
| `/edges` | 매장 중심을 곡선으로 잇는다. 선 굵기는 weight, 글자는 label이다. 한쪽 끝이 다른 층 매장이면 캔버스 오른쪽 가장자리의 층 배지로 잇는다. 배지를 누르면 그 층으로 이동한다. 같은 데이터로 관계 그래프를 그린다. |
| `/focus` | 현재 층에 있는 대상 매장의 경계 상자로 확대·이동한다. 대상 매장이 다른 층에 있으면 그 층을 표시할 때 적용한다. |
| `/panel` | `changes`·`artifact`는 개정 검토 탭, `uploads`는 개정 검토 탭의 업로드 영역(`job_id`가 있으면 그 작업), `layout`은 레이아웃 대안 탭을 연다. `layout`의 `{brief_id}`는 시즌 개편 화면에서 그 브리프를, `{rev, floors, alternatives}`는 배치 대안 화면을 연다. `table`은 도면 캔버스 아래쪽에 표 패널을 연다. `journey`는 도면 왼쪽 위에 고객 동선 카드를 연다. `none`과 모르는 유형은 탭을 바꾸지 않는다. |
| `/journey` | 고객 한 명의 하루 쇼핑 동선이다. 현재 층의 `segments`를 흰 테두리가 있는 주황 선으로, 현재 층의 `stops`를 번호 원과 결제 시각으로 그린다. 층이 바뀌는 구간 끝에는 "→ 3층 (ESC-A)", 도착 구간 시작에는 "1층에서 올라옴"을 표시한다. 동선은 강조·연결선 위에 그린다. `null`이면 지운다. 기본값이 `null`이므로 `replace` 패치를 바로 적용할 수 있다. |
| `/route` | 두 지점 사이의 길 찾기 경로다. 현재 층의 `segments`를 흰 테두리가 있는 파란 선(`#1e88e5`)으로 그린다. 현재 층에 있는 출발 지점은 "출발"이라고 쓴 초록 원, 도착 지점은 "도착"이라고 쓴 파란 원과 둘레의 고리로 그리고, 옆에 지점 이름(`label`)을 붙인다. 층 이동 라벨은 동선과 같다("→ 8층 (ESC-A)", "1층에서 올라옴"). 경로는 강조·연결선 위, 고객 동선 아래에 그린다. 길 찾기 상자를 띄우고, 경로가 지나는 층 탭에 표시한다. `null`이면 지운다. 기본값이 `null`이므로 `replace` 패치를 바로 적용할 수 있다. |
| `/flow` | 통로 위 집계(추정 유동, 팝업 후보, 통로 폭·피난 점검)다. 현재 층의 `segments`를 흰 테두리가 있는 선으로 그린다. 굵기는 `weight`에 따라 2~10 px, 색은 옅은 파랑에서 짙은 보라까지이고, `color`가 있으면 그 색(예: 피난 점검의 빨강)을 쓴다. 가벼운 선을 먼저 그려 많은 구간이 위에 보인다. 현재 층의 `markers`는 번호 원으로 그린다(통로 위 후보 공간은 호박색, 공실·팝업 매장은 청록, 피난 거리 초과 지점은 빨강). 선은 통로 위(강조·라벨 아래)에, 번호 원은 연결선 위에 그린다. 통로 집계 상자를 띄우고, 데이터가 있는 층 탭과 범례에 표시한다. `null`이면 지운다. 기본값이 `null`이므로 `replace` 패치를 바로 적용할 수 있다. |

고객 동선, 길 찾기 경로, 통로 집계는 단독으로 표시한다(계약 3절). 패치가 셋 중 하나를 값으로 바꾸면(`/journey`, `/route`, `/flow` 자체를 객체로 `replace`·`add`) 나머지 둘을 `null`로 바꾸고, 같은 패치가 함께 바꾸지 않은 `heatmap`, `highlights`, `edges`, `compareRev`도 비운다. 백엔드의 `ui_show_journey`, `ui_show_route`, `ui_show_flow`가 보내는 패치와 결과가 같고, 사용자의 화면 조작(예: "다른 고객 보기")과 이 규칙을 지키지 않는 백엔드에서도 표시가 하나로 유지된다. 하위 필드 패치(`/flow/caveat`)와 `null` 패치는 다른 표시를 지우지 않는다. 이후 답변의 heatmap·강조·연결선·개정 비교가 동선·경로·집계를 지우는 규칙은 답변의 경계를 아는 백엔드가 처리한다.

동선 카드, 길 찾기 상자, 통로 집계 상자가 열려 있으면 층 전체 보기와 매장 초점을 카드 오른쪽 영역에 맞춘다. 새 동선, 새 경로, 새 집계가 오면 다시 맞춘다. 카드를 닫거나 표시를 지우면 그만큼 다시 이동한다.

매장의 층은 매장 코드의 앞부분(`{floor}-{band}{nn}`, [CAD 규약](../../docs/specs/cad-conventions.md))으로 판단한다. 예를 들어 `2F-C03`의 층은 `2F`다.

추천 질문은 아래 시나리오를 실행한다. 시나리오는 백엔드와 같은 형식으로 `label`이 붙은 도구 호출(전문 에이전트 안의 중첩 호출 포함), `STATE_DELTA`, 작은 조각으로 스트리밍하는 답변 하나를 보낸다. 모의 데이터에는 4층이 없으므로 4층 질문은 3층으로 대신 답하고 답변 첫 줄에 그 사실을 밝힌다. 백엔드와 같이 길 찾기 경로, 고객 동선, 통로 집계는 서로를 지우고, 이후의 heatmap·강조·연결선·개정 비교 표시는 셋 다 지운다.

| 질문 | 화면 변화 |
|---|---|
| S/S 개편 도면에서 뭐가 바뀌었는지 알려줘 | R1과 R0를 비교하고, 변경 매장을 강조하고, 개정 검토 탭을 연다. |
| 4층에서 효율이 낮은 매장과 이유를 보여줘 | 공간 생산성 전문 에이전트 단계(중첩 단계 3개) 뒤에 평효율 heatmap, 저효율 매장 2개 강조, 연결선 3개(1F 연결 포함), 확대 이동 |
| 40대 VIP 고객은 화장품이랑 뭘 같이 사? | 1층 화장품 매장 중심의 교차구매 연결선 5개(층간 연결 포함)와 화장품 매장 강조. 관계 그래프 탭에 같은 관계를 표시한다. |
| VIP 고객 한 명의 쇼핑 동선을 보여줘 | 이전 표시를 지우고, 첫 결제 층(1F)으로 이동해 동선을 그리고, 동선 카드를 연다. "다른 고객 보기"로 2·3번째 고객을 볼 수 있다. |
| 정문에서 3층까지 가는 길 알려줘 | 경로 계산 단계 뒤에 정문(ENT-1)에서 3층 Cafe Halune(3F-C05)까지 경로를 그리고(에스컬레이터 A, 걷는 거리 85 m), 출발 층(1F)으로 이동해 길 찾기 상자를 띄운다. 답변은 걷는 구간과 층 이동을 순서대로 설명한다. |
| 주말 팝업 어디가 좋아? | 팝업 후보 계산 단계 뒤에 주말 추정 유동과 팝업 후보 5곳(1F 2곳, 3F 3곳, 그중 하나는 팝업 매장 3F-P01)을 그리고, 1순위 후보의 층(1F)으로 이동해 통로 집계 상자를 띄운다. |
| 4층 재배치안 3개 만들어 비교해줘 | 레이아웃 대안 탭에 대안 3개를 열고, 추천안의 이동 경로를 도면에 표시한다. |

이 밖에 “3층 평효율 표로 보여줘”는 표 패널(`panel.type = table`)을 연다. 매장 코드(예: `3F-C02`)를 넣은 질문은 해당 매장의 KPI를 요약한다. 길 찾기 질문("가는 길", "어떻게 가", "까지 경로" 등)은 매장 코드나 브랜드 이름이 있으면 그 매장으로, 없으면 마지막으로 말한 층의 기본 매장으로 안내한다. "서측"·"동측"은 출발 출입구를, "엘리베이터"는 수직 이동 수단을 바꾼다. "유동", "붐비" 같은 질문은 추정 유동을, "통로 폭", "피난", "비상구" 질문은 통로 폭·피난 점검을 그린다. 고객군("40대 여성 VIP"), 요일("주말", "평일"), 시간대("10~14시", "오후")와 층을 읽어 조건으로 쓴다.

## 7. 계약 해석

계약에 명시되지 않은 부분은 아래와 같이 처리한다. 계약 문서를 바꿀 때 함께 검토한다.

| 항목 | 웹앱의 처리 |
|---|---|
| heatmap 끄기 | `heatmap: null`과 `heatmap.values: null`을 모두 “끔”으로 처리한다. |
| SSE 이벤트 구분 | 표준 형식(`data: {...}` 뒤 빈 줄)을 처리한다. 빈 줄 없이 한 줄에 JSON 하나를 보내도 처리한다. |
| 필드 이름 | 계약의 snake_case(`thread_id`, `message_id`, `tool_call_id`, `tool_name`)를 기준으로 한다. AG-UI SDK의 camelCase(`threadId`, `toolCallName` 등)도 받는다. |
| 알 수 없는 이벤트 | 계약에 없는 이벤트(예: `TOOL_CALL_ARGS`, `STATE_SNAPSHOT`)는 무시한다. |
| `facility` 형식 | 문자열 또는 `{code, name}` 객체를 받는다. |
| 카테고리 색 | `color`가 없으면 백엔드 층별 안내도 생성기와 같은 방식으로 색을 만든다. |
| `panel.payload` | `changes`: `{rev_from, rev_to}`, `artifact`: `{generator}`, `layout`: `{rev, floors, alternatives}`, `table`: `{title, columns, rows}`(행은 객체 또는 배열)로 해석한다. 키가 없으면 현재 상태로 대신한다. |
| 다른 층의 `focus` | 현재 층에 대상 매장이 없으면 그 층을 표시할 때 적용한다. |
| 양 끝이 모두 다른 층인 `edges` | 도면에는 그리지 않고 관계 그래프에만 표시한다. |
| `percentile` | 0~1과 0~100을 모두 받아 0~100으로 표시한다. |
| 산출물 파일 `url` | 없으면 `/api/artifacts/{rev}/{generator}/{path}`로 만든다. |
| 검토 오류 | 오류 응답의 `detail`을 산출물 카드에 표시한다. |
| 레이아웃 `constraints` | `{max_moves, keep_anchors}`를 보낸다. 작업 중인 백엔드 구현이 제약을 키워드 인자로 받으므로 키 이름을 그 구현에 맞췄다. |
| 레이아웃 대안 형식 | 계약 형식(`id`, `kpi_delta`, `constraints`)과 레이아웃 엔진 형식(`alt_id`, `delta_krw`, `objective_low/high`, `constraint_checks`)을 모두 받아 같은 화면으로 표시한다. |
| 채팅 `ui_state` | 계약대로 `rev`, `floor`, `selection`만 보낸다. |
| `label`이 없는 도구 호출 | 도구 이름을 한국어 라벨로 바꾼다(`src/lib/chatRun.ts`의 `TOOL_LABELS`, 예: `analytics_productivity` → "공간 생산성 계산"). `analytics.productivity`처럼 점으로 구분한 이름과 서버 접두사가 붙은 이름도 같은 라벨로 바꾼다. 표에 없는 이름은 접두사(`analytics_` → "데이터 분석")로 정하고, 그래도 없으면 "작업 중"으로 표시한다. |
| `label`이 없는 UI 도구 | 적용한 패치로 라벨을 구체화한다. 예: `ui_set_floor` → "4층으로 이동", `ui_highlight_units` → "매장 5곳 강조", `ui_show_panel` → "변경 목록 열기", `ui_show_route` → "경로 그리기"(`route: null`이면 "경로 지우기") |
| `ok`가 없는 `TOOL_CALL_END` | `summary`가 "오류:"로 시작하거나 `{"ok": false`로 시작하면 실패로 표시한다(현재 백엔드의 표기). |
| 중첩 호출 | `parent_tool_call_id`의 상위 단계가 없으면 최상위 단계로 표시한다. 상위 단계가 끝나면 진행 중인 하위 단계도 끝난 것으로 본다. |
| 큰 조각의 텍스트 | 조각 크기와 관계없이 같은 방식으로 이어 붙여 표시한다. |
| `journey` 정규화 | 결제 정류장이 하나도 없으면 `null`로 본다. `order`가 없으면 순서대로 번호를 매기고, `floor`가 없으면 매장 코드에서 층을 읽는다. 좌표가 없는 정류장은 목록에만 표시한다. 점이 2개 미만인 `segments`는 그리지 않는다. `transitions`가 없으면 연속한 정류장의 층 변화로 만든다. `summary`가 없으면 정류장으로 계산한다. |
| 층 이동 라벨 위치 | 같은 결제 순서(`from_order`, `to_order`)를 가진 출발 층·도착 층 `segments`의 끝점과 시작점에 둔다. 해당 `segment`가 없으면 정류장 위치에 둔다. 위·아래 방향은 `/api/meta`의 `ordinal`로 정한다. |
| 다른 고객 보기 | `journey.query.segment`를 `age_band:40s;gender:F;tier:VIP\|VVIP` 형식으로 바꾸고 `rank`에 1을 더해 `GET /api/analytics/journey`를 호출한다. `journey.query.rev`가 있으면 함께 보내 같은 개정 기간에서 고른다. 응답에 `query`가 없으면 요청한 값을 채운다. 응답의 `rev`가 화면의 개정과 다르면 `/rev`도 바꾼다. 404이면 "더 보여 줄 고객이 없어요"를 표시한다. |
| `route` 정규화 | `origin`과 `destination`이 객체이고 층을 알 수 있어야 경로로 본다. 그렇지 않으면 `null`이다. `floor`가 없으면 `unit_code`나 층을 붙인 `ref`(`1F:ESC-A`, `3F-C05`)에서 읽는다. `ENT-1`처럼 층이 없는 `ref`만으로는 층을 정하지 않는다. `label`이 없으면 `ref`를, `title`이 없으면 "출발 label → 도착 label"을 쓴다. 숫자 문자열은 숫자로 바꾸고, 좌표가 잘못된 점과 점이 없는 `segments`는 버린다. 점이 2개 미만인 `segments`는 그리지 않는다. 출발 층과 도착 층이 다른데 쓸 수 있는 `transitions`가 없으면 수직동선을 모르는 층 이동 하나를 만든다. 같은 층 사이의 `transitions`는 버린다. |
| 경로의 층 이동 라벨 | `transitions`의 i번째 항목은 `segments`의 i번째(떠나는 층)와 i+1번째(도착하는 층)에 대응한다고 보고, 층이 맞지 않으면 그 층의 `segment`를 찾는다. 해당 층에 `segment`가 없으면 그 층에 있는 출발·도착 지점에 라벨을 둔다. 위·아래 방향은 `/api/meta`의 `ordinal`로 정한다. |
| 경로가 지나는 층 | 층 탭과 길 찾기 상자에는 출발 층, `transitions`의 층, `segments`의 층, 도착 층을 표시한다. 에스컬레이터를 타고 지나치기만 하는 중간 층(예: 1F→8F의 2F~7F)은 그릴 것이 없으므로 표시하지 않는다. |
| 경로 요약 칩 | "걷는 거리 {walk_m}m"와 층 이동마다 "{수직동선} · {floors}개 층 이동 · 높이 {height_m}m"를 표시한다. `via`가 없으면 `via_type`(에스컬레이터·엘리베이터)을, `floors`가 없으면 층 `ordinal`의 차이를 쓴다. |
| 동선·경로·집계를 함께 받은 경우 | 계약 3절대로 하나만 표시한다. 한 패치에 둘 이상이 값으로 오면 마지막 연산의 표시만 남긴다. 규칙은 4절에 있다. |
| `route.rev` | 웹앱은 `/rev`를 바꾸지 않는다. 화면의 개정과 다르면 길 찾기 상자에 "R2 도면으로 계산한 경로예요. 지금은 R1 도면을 보고 있어요."를 표시한다. |
| `GET /api/spatial/route` | 웹앱은 이 REST 경로를 직접 호출하지 않는다. 경로는 에이전트의 `ui_show_route`가 보내는 `STATE_DELTA`로만 받는다. |
| `flow` 정규화 | `mode`, `floors`, `markers` 중 하나도 없는 값과 객체가 아닌 값은 `null`로 본다. 그린 것이 없는 집계(좁은 통로가 없는 점검 결과)는 그대로 표시한다. 점이 2개 미만인 `segments`, 좌표나 층을 알 수 없는 `markers`는 버린다. `marker.floor`가 없으면 `unit_code`에서 층을 읽는다. `floors`가 `{floor, ...}` 목록으로 와도 받는다. 숫자 문자열은 숫자로 바꾼다. |
| `flow` 선 굵기와 색 | `weight`(0~1로 자름)로 정한다. `weight`가 없으면 `value / max_value`로 계산하고(통로 폭·피난 점검은 값이 폭이라 계산하지 않음), 그래도 없으면 중간값으로 그린다. `color`는 16진수 색일 때만 쓴다. |
| 알 수 없는 `flow.mode` | "통로 집계"라고 표시하고 추정 유동처럼 그린다. 알 수 없는 `marker.kind`는 통로 위 후보 공간 색으로 그린다. |
| `flow` 층 표시와 요약 | 층 탭과 상자의 층 목록은 실제로 그릴 선이나 번호 원이 있는 층이다(`summary.floors`가 아님). 요약 칩은 추정 유동·팝업 후보에서 `summary.customer_days`, `summary.trips`, 층 수(2개 이상), 후보 수이고, 통로 폭·피난 점검에서는 받은 선과 경고 지점의 수, 기준 폭·기준 거리(`summary` 또는 `query`의 `min_width_m`, `max_travel_m`)다. |
| `flow.rev` | 웹앱은 `/rev`를 바꾸지 않는다. 화면의 개정과 다르면 상자에 "R2 도면으로 계산했어요. 지금은 R1 도면을 보고 있어요."를 표시한다. |
| `GET /api/spatial/flow` | 데이터 소스에 `getFlow`가 있지만 화면에서는 부르지 않는다. 통로 집계는 에이전트의 `ui_show_flow`가 보내는 `STATE_DELTA`로 받는다. |
| 공사 순서 요청 | `POST /api/relayout/{brief_id}/phasing`에 `crews`, `fitout_weeks`, `use_temporary`만 보낸다. `alt_id`를 보내지 않아 백엔드가 대상을 정한다(결정한 대안, 없으면 순효과가 가장 큰 대안). 화면은 같은 규칙으로 예상 대상을 미리 보여 준다. 입력 기본값은 저장된 결과의 `params`, 없으면 2 / 브리프의 공사 기간 / 사용이다. |
| 저장된 공사 순서 | `project.phasing`을 그대로 보여 준다. `phasing.alt_id`가 지금 대상과 다르면 다시 계산하라고 알린다. 새 대안을 만들면 화면에서도 결과를 지운다(백엔드도 지운다). |
| 공사 작업 칩 | `action`을 짧은 칩(퇴점, 이전, 입점, 임시 영업, 휴점)으로 보이고, 백엔드의 `action_label`은 칩의 설명(`title`)과 "작업 설명 보기"에 쓴다. 모르는 `action`은 `action_label`을 그대로 칩에 쓴다. |
| 공사 순서 손실 | `lost_krw`(영업 손실 추정), `naive_lost_krw`(모두 공사 기간만큼 휴점할 때), `entry_delay_krw`(0보다 클 때만 "입점 지연 기회 손실")를 앱의 금액 형식(1억 원 이상은 "6.2억 원", 그 아래는 "6,648만 원")으로 보인다. `saved_krw`는 따로 표시하지 않는다. 늦어진 입점은 `entries[].earliest_week`를 함께 보인다. |
| 개편 성과 보고서 링크 | 실제 개정이고, `parent_rev_id`가 있고, `has_sales`가 `true`일 때만 보인다(`has_sales`가 없으면 보이지 않음). 주소는 `/api/reports/relayout-review/{rev}?window_days=90`이고 30일도 고를 수 있다. 새 탭(`rel="noopener noreferrer"`)으로 연다. |
| 점포 비교·개편 성과 API | `GET /api/analytics/stores`와 `GET /api/analytics/relayout-review`는 데이터 소스(`getStoreComparison`, `getRelayoutReview`)와 모의 응답만 있고 화면에서는 부르지 않는다. 에이전트가 같은 도구로 답한다. |
| 메타데이터 종류 | `stores`(비교 점포)와 `store_kpis`(점포 실적)를 종류 선택에 넣고 CSV·XLSX를 받는다. |
| 개정 표시 | "업로드"는 `model_source`로 판단한다. `source`는 도구 설명 문자열이라 쓰지 않는다. "실적 없음"은 실제 개정의 `has_sales`가 `false`일 때만 붙인다. `has_sales`가 없으면 실적이 있다고 본다. |
| 오류 응답 | 400·404·409의 `detail` 문자열을 그대로 보여 준다. 422의 검증 오류 목록은 `msg`를 이어 붙인다. |
| `layout`의 `brief_id`와 `alternatives` | 둘 다 오면 시즌 개편 화면을 열고 배치 대안 결과도 받아 둔다. |
| 대안 `ALT-0` | `alt_id`가 `ALT-0`이거나 `rev_id`가 `-A0`으로 끝나면 기준안으로 표시한다. KPI는 다른 대안과 같은 칸으로 보여 준다(기준안 대비 변화는 0). 처음 펼칠 카드를 고를 때는 제외한다. |
| 대안의 `explanations` | 변경별 설명은 `changes[].explanation`에 있고, `explanations`에는 추가 참고(신규 입점 위치 조정, 이웃 매장 파급 효과)만 온다고 보고 "근거 보기" 안의 "참고"로 보여 준다. |

## 8. 접근성

- 모든 버튼에는 글자 또는 `aria-label`이 있다.
- 키보드 포커스는 파란 외곽선으로 표시한다. 채팅 입력창은 입력 상자 전체에 포커스 테두리를 표시한다.
- 층 탭과 패널 탭은 화살표 키, Home, End로 이동한다.
- 범례와 제약 조건은 색과 함께 글자로 의미를 표시한다.
- 관계 그래프의 노드는 Tab과 Enter로 조작한다. 같은 관계를 표(연결 목록)로도 제공한다.
- 한글 입력 중 조합을 확정하는 Enter는 메시지를 보내지 않는다.
- 채팅의 상태 줄은 `role="status"`(aria-live)로 읽힌다. 답변 완료와 오류도 별도의 live 영역으로 알린다. 스트리밍 중인 본문은 읽지 않는다.
- 작업 과정 버튼은 `aria-expanded`, 기술 정보 버튼은 `aria-pressed`로 상태를 알린다. 단계 표시(완료·진행 중·실패)에는 글자 대체 텍스트가 있다.
- 동선 카드의 결제 항목은 버튼이다. 선택한 항목은 `aria-current`로 알린다. Esc 키로 카드를 닫는다. 층 탭의 결제 수 배지는 "(고객 동선 결제 3곳)"으로 읽힌다.
- 길 찾기 상자의 층 버튼은 "1층 출발, 도면 보기"로 읽히고, 지금 보고 있는 층은 `aria-current`로 알린다. 상자 안에서 Esc 키를 누르면 경로를 지운다. 층 탭의 경로 표시는 "(길 찾기 경로: 출발 층)"으로 읽힌다.
- 통로 집계 상자의 층과 후보 지점은 버튼이다(예: "후보 1 · 1F 서측 횡단 통로, 1층 도면에서 보기". 제목이 번호로 시작하지 않으면 "1. "을 앞에 붙인다). 상자 안에서 Esc 키를 누르면 집계를 지운다. 층 탭의 표시는 "(팝업 후보 2곳)"처럼 읽힌다. 도면의 선 굵기·색은 범례와 상자에서 글자로도 설명한다.
- 공사 순서 블록은 계산하는 동안 `aria-busy`이고, 시작과 결과(전체 기간, 영업 손실)를 live 영역으로 알린다. 표는 숨긴 `caption`과 열 머리글을 갖고, "작업 설명 보기"는 `aria-pressed`로 상태를 알린다. 입력 칸에는 모두 레이블이 있다.
- 개편 성과 보고서의 비교 기간 선택에는 레이블이 있고, 링크의 설명(`title`)은 비교 기준을 알린다.
- 움직임 줄이기(`prefers-reduced-motion`) 설정에서는 상태 줄, 커서, 진행 표시의 애니메이션을 끈다.

## 9. 제한 사항

- 모의 데이터는 1F와 3F만 제공한다. 다른 층의 매장은 층 배지와 관계 그래프에서 매장 코드로 표시한다. 다른 층을 묻는 질문은 3층으로 대신 답한다.
- 고객 동선은 결제 기록의 순서로 추정한 경로다. 실제로 걸은 길이 아니다.
- 길 찾기의 걷는 거리는 출발 층과 도착 층의 통로망 최단 경로 길이다. 에스컬레이터를 타는 구간과 층마다 갈아타는 거리는 넣지 않는다.
- 추정 유동은 결제 기록과 통로망으로 추정한 값이다. 실제 계수 장비 데이터가 아니다. 통로 폭·피난 점검은 도면 기하로 계산한 참고 자료이며 법규 판정을 대신하지 않는다.
- 공사 순서는 공사 기간과 손실을 단순한 규칙으로 추정한 결과다. 실제 공정표는 시공사와 확정한다.
- 화면 테스트는 WebGL 렌더링 결과를 검사하지 않는다. 도면 렌더링은 브라우저에서 확인한다.
- 빌드의 기본 JavaScript 파일은 약 1.2 MB(gzip 약 350 KB)다. 대부분 deck.gl이다.
